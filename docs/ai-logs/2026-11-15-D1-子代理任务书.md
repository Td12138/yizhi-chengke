# 2026-11-15 · D1 · 并行子代理任务书

## 背景

作品实质工作量集中在一天内并行推进，采用「主会话定架构与验收标准，子代理按目录分包执行，主会话统一复核」的方式。五个任务书即为实际下发的原文，是本次 AI 协同开发过程的主要证据。

> 说明：任务书中提到的 `docs/方案设计.md` 是开发期的内部设计文档，未随仓库公开；其中与实现相关的结论已并入 `docs/技术文档.md`。除此之外任务书内容未作改写，仅将本机绝对路径归一化为相对路径。

## 协作规则（先定规则，再派活）

| 规则 | 原因 |
|---|---|
| 一个代理只碰一个目录 | 并行改写同一仓库，冲突比速度更贵 |
| 不执行任何 git 命令 | 提交历史必须由单一入口产出，否则会出现空提交与信息不可读 |
| 每条任务书自带验收命令 | 汇报必须贴真实输出，不接受「应该可以」 |
| 明确写出「做不到就降级」 | 防止在一条路上耗死 |
| 禁止写入密钥与真实地址 | 仓库公开 |

## 任务书一 · 后端 Provider 与测试

```
你是「一纸成课」比赛作品的后端工程师。仓库：projects/yizhi-chengke（独立 git 仓库，已推 GitHub）。今天 2026-11-15，省赛截止 11-18，时间紧，优先可用性而非完美。

先读：docs/方案设计.md、apps/server/ 下全部代码。

**只改 apps/server/ 下的文件，绝不改 apps/web/、docs/。**

任务：

1. Provider 走通真实模式：providers/vlm.py / providers/llm.py 目前只有 mock 和通用 OpenAI 兼容调用。在 config.py 增加按 provider 名自动补缺省的映射（仅在环境变量未显式设置时生效）：
   - qwen → https://dashscope.aliyuncs.com/compatible-mode/v1，视觉模型 qwen-vl-max，文本 qwen-plus
   - glm → https://open.bigmodel.cn/api/paas/v4，视觉 glm-4v-plus，文本 glm-4-plus
   - deepseek → https://api.deepseek.com/v1，文本 deepseek-chat
   显式环境变量优先。不要写入任何真实密钥，不要新建 .env。

2. 卡片修正闭环：新增
   - PATCH /api/cards/{card_id}：JSON 可选字段 {title,summary,formula,body}，更新后返回完整 card；不存在返回 404。
   - GET /api/sources/{source_id}：返回该来源的识别原文块与关联卡片。
   目的：让「识别错了能人工改」在界面上成立。

3. 自动化测试：新增 apps/server/tests/（pytest），覆盖：
   - orchestrator.judge 归一化与 choice/fill 判定
   - agents.verify.check_question：通过 / 驳回 / 无 verify 字段三态
   - db.search_cards 中文检索：查询「为什么这里要配方」必须召回「顶点式与对称轴」
   - 编排回环：mock 下 generate 第一轮必须被驳回 1 题、第二轮全通过（用 EventBus 收事件断言）
   跑法：<venv>/Scripts/python.exe -m pytest apps/server/tests -q，必要时 tests/conftest.py 处理 sys.path。除 pytest 之外不引入新依赖。

约束：不要执行任何 git 命令（不 add / 不 commit / 不 push）；不要启动长期服务占端口（测试体内同步调用即可，端口用 0 或 TestClient）；路径一律相对或由项目根推导；不写真实 IP / 域名 / 账号 / 密钥。

汇报：改动文件清单、pytest 实际输出、遗留问题。
```

**产出**：Provider 预设三级解析（显式 env > 预设 > 空）、两个新接口、6 个测试文件 42 个用例。
**验收**：主会话独立重跑 `pytest` → 42 passed；`git diff` 复查无硬编码盘符、无密钥。
**主动报出的遗留**：`corrected_by_user` 字段未落地（人工修正不留痕）、`normalize` 增加全角转半角属行为变化。前者进入 P1 清单，后者判定为判分缺陷修复，接受。

## 任务书五 · 独立评审

```
你是独立的作品评审专家，与开发过程无关，不采信开发者自述。任务是对参赛作品做交付前审查。

只审查 git 跟踪的文件（以 git ls-files 为准），工作区里未跟踪的内部材料不在范围。
apps/desktop/ 正在并行开发，排除。

必须实际执行：
1. pytest 全量
2. 前端 npm run build
3. 从零复现：严格按 README 步骤走一遍（临时目录 + 临时端口），确认「照做能跑起来」
4. 真实启动后端，跑 ingest 与 generate，确认事件流完整生命周期
5. 密钥与隐私扫描：git log -p --all 与工作树中检索密钥特征、内网 IP、邮箱、绝对路径
6. 文档与代码一致性抽查（≥5 处）
7. git log --oneline 评估提交粒度是否属于「一次性提交」

输出：P0/P1/P2 缺陷表，每条带 文件:行 + 期望行为 + 证据；另附「实际执行过的验证」与「检查过但没问题的项」。
不确定的写「存疑」并说明，不要猜。
不要修改任何文件，不要执行 git 写操作，不要启动长期占端口的服务。
```

**为什么要有这一条**：写代码的人不会发现自己的盲区，AI 也一样。审查必须在全新上下文里跑，只给文件路径与赛事要求，不告诉它「我们做得挺好」。
